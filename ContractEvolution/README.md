# ContractEvolution — что ломается у отстающих, когда меняется контракт

Контракты событий мы шарим через NuGet-пакет. Кто-то обновит пакет не сразу, и его сервис будет читать **новые** события **старой** версией контракта. Здесь проверяется, у кого и на чём это ломается.

Как это работает:

1. **ContractGen** (source generator) читает описание `OrderCreated.contract` и во время сборки генерирует все версии класса `OrderCreated`.
2. **CompatCheck** для каждой версии генерирует события: одно обычное и по одному на каждое граничное значение каждого поля.
3. Каждое событие читается каждой версией контракта не новее его самого — так, как его прочитал бы отстающий сервис. Делается это через `IConverter` из MessageCheck.
4. Отправленный JSON сравнивается с тем, что увидел потребитель: что упало, что потерялось, что изменилось.

## Структура

```
src/ContractGen/          — source generator (netstandard2.0)
  ContractSpec.cs         — разбор описания контракта
  ContractGenerator.cs    — генерация классов по описанию
src/Contracts/            — «пакет с контрактами»
  OrderCreated.contract   — описание: как менялся OrderCreated
src/CompatCheck/          — генератор событий + проверка
  EventFactory.cs         — события с граничными значениями
  Compat.cs               — чтение старой версией и сравнение
  Report.cs               — матрица и отчёт compat-report.md
  Program.cs              — запуск; режим kafka
tests/CompatCheck.Tests/  — тесты, которые фиксируют поведение
```

## Описание контракта

```
contract OrderCreated
v1 OrderId:string Amount:int Quantity:int Comment:string
v2 +Currency:string      # добавили поле
v3 -Comment              # удалили поле
v4 ~Quantity:long        # int → long
v5 ~Amount:double        # int → double
v6 ~OrderId:int          # string → int
```

В строке `v1` перечислены все поля. Дальше каждая строка описывает изменение относительно предыдущей версии: `+поле:тип` — поле добавили, `-поле` — удалили, `~поле:тип` — поменяли тип.

Из этого описания генератор делает `Contracts.V1.OrderCreated` … `Contracts.V6.OrderCreated` и список `Contracts.OrderCreatedVersions.All`. Тип везде называется одинаково, `OrderCreated`, а разные namespace изображают разные версии пакета. Сгенерированный код можно посмотреть в `src/Contracts/obj/Debug/net8.0/generated/`.

Если описание написано с ошибкой, например удаляется поле, которого нет, сборка упадёт с понятной ошибкой `CG001`.

Почему описание в простом текстовом формате, а не в JSON: генератор обязан собираться под netstandard2.0, и подключить туда System.Text.Json сложно. Текстовый формат разбирается в 50 строк.

## Запуск

Нужна ветка, где MessageCheck уже с `IConverter` и `HeaderReader` (PR #1).

```bash
cd ContractEvolution

# тесты — Kafka не нужна
dotnet test tests/CompatCheck.Tests

# матрица совместимости, события генерируются в памяти
cd src/CompatCheck
dotnet run

# то же, но события сначала публикуются в Kafka (заголовки eventType/version/case),
# читаются обратно и проверяются уже байты из топика
dotnet run -- kafka
```

Отчёт пишется в `compat-report.md`.

## Результат

Потребитель — System.Text.Json с Web-настройками: camelCase, регистр имён не важен, **лишние поля игнорируются**.

| отправил ↓ / читает → | v1 | v2 | v3 | v4 | v5 | v6 |
|---|---|---|---|---|---|---|
| **v1** | ✅ |  |  |  |  |  |
| **v2** | ➕ 13/13 | ✅ |  |  |  |  |
| **v3** | ⚠️ 11/11 | ⚠️ 11/11 | ✅ |  |  |  |
| **v4** | 💥 3/11 | 💥 3/11 | 💥 3/11 | ✅ |  |  |
| **v5** | 💥 5/11 | 💥 5/11 | 💥 5/11 | 💥 2/11 | ✅ |  |
| **v6** | 💥 12/12 | 💥 12/12 | 💥 12/12 | 💥 12/12 | 💥 12/12 | ✅ |

Обозначения:
- ✅ — прочиталось без потерь;
- ➕ — прочиталось, новые поля старый контракт просто не видит;
- ⚠️ — прочиталось **без ошибки**, но данные не те;
- 💥 — десериализация упала.

Число в ячейке — сколько событий из скольких закончились этим исходом.

Что из этого следует:

| Изменение | Что видит отстающий |
|---|---|
| **Добавили поле** (v2) | Ничего не ломается: новое поле игнорируется. Но если в настройках запрещены лишние поля (`UnmappedMemberHandling.Disallow`, так сейчас в MessageCheck), падает **каждое** событие. |
| **Удалили поле** (v3) | Исключения нет, но поле молча становится default (`""`, `0`). Опаснее всего: ошибку никто не заметит. |
| **int → long** (v4) | Работает, пока значение влезает в int. На `int.MaxValue + 1` и `int.MinValue − 1` — `JsonException`. |
| **int → double** (v5) | Падает только на дробных (`1.5`) и огромных (`1e20`) значениях. `2.0` System.Text.Json пишет как `2`, и старый int его спокойно читает. |
| **string → int** (v6) | Сменился тип в самом JSON (string → number), поэтому падает каждое событие. |

Отсюда видно, почему эти проверки должны быть автотестами (`tests/CompatCheck.Tests`). Половина поломок зависит от значений, а не от типа, и поведение десериализатора может поменяться при обновлении .NET.

## Допущения — нужно подтвердить

- Версии моделируются разными namespace в одном проекте, а не отдельными NuGet-пакетами.
- Продюсер и потребитель — System.Text.Json с Web-настройками. Если сервисы используют Newtonsoft.Json или другие настройки, результат может отличаться.
- Удалённое поле, молча ставшее default, считается поломкой (⚠️).
