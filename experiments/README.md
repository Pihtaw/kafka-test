## ТЕСТ1. В какую партицию попадает один и тот же orderId

**Что?** 

Если два сервиса пишут один и тот же ключ, но разными клиентами (.NET и Java / Redpanda Connect), попадёт ли ключ в одну и ту же партицию?

**Как?** 

Партиция = хэш(ключ) % число партиций. Но хэш у клиентов разный:

| Клиент | Партиционер по умолчанию | Формула |
|---|---|---|
| .NET (Confluent.Kafka / librdkafka) | `consistent_random` | CRC32(ключ) % n |
| Java-клиент, Redpanda Connect | murmur2 | (murmur2(ключ) & 0x7fffffff) % n |

**Результат**:

```
dotnet run -- hash

orderId | .NET дефолт | .NET Murmur2 | CRC32 % n | murmur2 % n | совпали?

    102 |           0 |            0 |         0 |           0 | да
    103 |           0 |            2 |         0 |           2 | НЕТ
    104 |           0 |            2 |         0 |           2 | НЕТ

    106 |           0 |            0 |         0 |           0 | да

    110 |           2 |            1 |         2 |           1 | НЕТ

Один и тот же orderId попал в РАЗНЫЕ партиции у 14 из 20 ключей.
```

**Размышления** 

Из 20 orderId в разные партиции попали: 14 .
Если исходный топик писал один клиент, а мы перекладываем другим, то порядок событий одного заказа может нарушиться: события одного orderId окажутся в разных партициях. Чтобы этого не было, нужно либо использовать тот же партиционер, что у исходного продюсера (в .NET `Partitioner = Partitioner.Murmur2`), либо явно указывать партицию.

## ТЕСТ 2. Идёт ли CreateTime по возрастанию внутри партиции

**Что?** 

Всегда ли внутри одной партиции время сообщений только растёт. От этого зависит, точно ли окно по времени с-по превращается в диапазон offsets.

**Как?** 

При `CreateTime` время сообщению ставит отправитель, а не брокер. В тесте несколько продюсеров параллельно пишут в одну партицию. Каждый продюсер копит сообщения в пачку (`LingerMs = 20`) и отправляет её целиком, а пачки ложатся в лог в порядке прихода на брокер, а не в порядке времени внутри них.

идет назад по времени = время сообщения меньше максимального времени среди сообщений, прочитанных до него(у которых меньше offset)

В пр dry-run такие моменты учтены(теоретически знали про проблему, но сейчас проверили на практике).
проверяем: до Start(первый offset со временем >= T1) < T1 - не читаем
внутри [Start; End)	вне окна - проставляем каждой записи outsideWindow
после End	внутри окна (опоздавшее, время < T2)	не читаем

**Запуск**

```
dotnet run -- time 4 2000          # 4 продюсера × 2000 сообщений, часы у всех одинаковые
dotnet run -- time 4 2000 1500     # у продюсера 0 часы отстают на 1,5 с
```

**Результат**

```
$ dotnet run -- time 4 2000
4 продюсеров × 2000 сообщений → time-test
Прочитано 8000 сообщений (offsets 0..7999)
Время шло назад у 5337 сообщений (66.71%)
Максимальный откат: 5 мс

$ dotnet run -- time 4 2000 1500
4 продюсеров × 2000 сообщений → time-test, у продюсера 0 часы отстают на 1500 мс
Прочитано 8000 сообщений (offsets 8000..15999)
Время шло назад у 5334 сообщений (66.67%)
Максимальный откат: 1506 мс
```

| Запуск | Прочитано | Время шло назад | Доля | Максимальный откат |
|---|---|---|---|---|
| 4 продюсера, часы одинаковые | 8000 | 5337 | 66,7% | 5 мс |
| 4 продюсера, у одного часы отстают на 1,5 с | 8000 | 5334 | 66,7% | 1506 мс |

**Размышления**

1. Порядок по offset не совпадает с порядком по времени. Откат при этом маленький, до 5 мс: судя по всему, примерно столько продюсер копит и отправляет пачку.
2. Размер отката определяется расхождением часов между отправителями. В эксперименте с отставанием на 1500 мс максимальный откат стал 1500+6 мс (то есть не увеличилось, остались те же 5мс примерно)


Можем уловить в [T1;T2) <T1 и >T2. Нужно искулючать сообщения внутри номеров и вне времени.
