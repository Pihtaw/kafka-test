# KafkaReplay — проверка и перенос событий Kafka

Утилита командной строки `replay`. Читает топик за **промежуток времени**, проверяет каждое событие **заданной версией контрактов** (DTO), показывает, что увидит сервис (отличия), и строит **план отправки**. С флагом `--execute` отправляет прошедшие проверку события в целевые топики **строго по плану** с сохранением ключа, заголовков и тела, ставит каждой записи один из пяти статусов и **побайтово сверяет** отправленное.

```
без --execute (ничего не отправляет):
  топик → окно по времени → offsets по каждой партиции (Assign, без коммита, границы фиксируются до чтения)
        → заголовки → тип события (Event-Type) → класс контракта → решение + причина + отличия
        → таблица маршрутизации → целевой топик и партиция
        → report.json, report.md, plan.json (исходные байты, решения, цели, контрольные суммы)

--execute (только из plan.json):
  проверка всех сумм (любое несовпадение — полный блок) → отправка → 5 статусов
  → чтение отправленного из цели → сравнение ключа, заголовков и тела байт в байт
  → execution.json, execution.md
```

## Что нужно

- Docker (для локальной Kafka);
- .NET 10 SDK: `dotnet --list-sdks` показывает `10.x`;
- Python 3 — только для проверки на дампе Event Hubs (раздел ниже).

Сборка строгая: предупреждения компилятора и анализаторов (Sonar, Meziantou, VS Threading) считаются ошибками (`Directory.Build.props`), версии пакетов — в одном месте (`Directory.Packages.props`), стиль — в `.editorconfig`.

## Быстрый старт: весь цикл одной командой

```bash
dotnet test             # из корня: KafkaReplay.slnx, Kafka для тестов не нужна
scripts/demo.sh         # Kafka → Seeder → проверка и план → отправка → сверка → повторный запуск
```

Что должно получиться в `demo.sh`:

1. Поднимется Kafka; Seeder запишет 15 событий в `orders-multi` (наши, чужие и битые) и создаст топик-цель `orders-copy`.
2. **Проверка и план.** Allowed 5, Skipped 3, Rejected 5, ConversionError 2; `✅ Сводка сходится`; `План отправки: … к отправке 5 из 15`; код выхода **1** (в данных есть отклонённые записи — так задумано).
3. **Отправка.** 5 строк «записано», «байты совпали»; статусы всех 15 записей: записано 5, отклонено проверкой 7, не отправлялось 3; `✅ Статусы сходятся`; код выхода **0**.
4. **Повторный запуск того же плана:** «К отправке в этот запуск: 0» — ничего не уходит второй раз; код выхода **0**.

Отчёты: `KafkaReplay/src/KafkaReplay/run-demo-…/` — `report.md`, `report.json`, `plan.json`, `execution.md`, `execution.json`.

Подробно, что Seeder кладёт в топик и какое решение ожидается для каждого события:

| Решение | Сколько | Какие |
|---|---|---|
| Allowed | 5 | OrderCreated 1.0.0 (два, у одного лишнее поле Comment), OrderCreated 1.1.0, OrderCancelled, OrderCreated 2.0.0 |
| Skipped | 3 | чужие PaymentCaptured и CourierAssigned, tombstone |
| Rejected | 5 | нет Event-Type, пустой Event-Type, не UTF-8, Event-Type дважды (разные и одинаковые) |
| ConversionError | 2 | оборванный JSON, пустое тело |

## Запуск по шагам

```bash
docker compose up -d kafka

# 1. Наполнить orders-multi учебными событиями. В конце Seeder печатает готовые команды для шага 2
cd Seeder && dotnet run

# 2. Проверка и план (команду с нужным временем скопировать из вывода Seeder)
cd ../KafkaReplay/src/KafkaReplay
dotnet run -- --bootstrap localhost:9092 --topic orders-multi --from "…" --to "…" \
  --routes ../../samples/routes.json --target-bootstrap localhost:9092

# 3. Отправка по плану: готовую команду с путём к plan.json печатает шаг 2
dotnet run -- --execute --plan run-…/plan.json --target-bootstrap localhost:9092
```

Без `--routes` утилита только проверяет и пишет отчёт, план не строится.

## Параметры

| Параметр | Что это |
|---|---|
| `--topic` | топик-источник |
| `--from`, `--to` | окно по времени `[from; to)`, формат `yyyy-MM-dd HH:mm:sszzz`, часовой пояс обязателен |
| `--bootstrap` / `--source-env` | источник: адрес локальной Kafka или имя переменной окружения со строкой подключения |
| `--contracts` | сборка реестра контрактов (`Dodo.EventRegistry.dll`); без него — встроенные учебные контракты |
| `--routes` | таблица маршрутизации; с ней пишется `plan.json` |
| `--target-bootstrap` / `--target-env` | цель: так же, как источник; нужна вместе с `--routes` и для `--execute` |
| `--partitioner` | как выбрать партицию в цели: `crc32` (как .NET-клиент, по умолчанию), `murmur2` (как Java), `keep` (как в источнике) |
| `--out` | папка для отчётов и плана, по умолчанию `run-<дата>-<время>` |
| `--execute --plan <plan.json>` | отправить по плану; источник и окно вместе с `--execute` указывать нельзя |

## Коды выхода

| Код | Проверка (без `--execute`) | Отправка (`--execute`) |
|---|---|---|
| 0 | всё прочитано, сводка сходится, отказов нет | всё из плана записано и совпало байт в байт |
| 1 | есть записи, отклонённые проверкой | есть «точно не записано», «результат неизвестен» или расхождения при сверке |
| 2 | диапазон дочитан не полностью или сводка не сходится | статусы не сходятся |
| 3 | не запустилась: параметры, подключение, контракты, маршрут в источник, нет целевого топика | блок: суммы плана, другая цель, отправка в источник |

## Подключение к кластеру

Для локальной Kafka достаточно адреса. Для настоящих кластеров — **строка подключения в формате Dodo.Kafka** (так подключаются сервисы):

| Кластер | Строка подключения |
|---|---|
| Kafka без входа | `BootstrapServers=host:9092;` |
| Azure Event Hubs (SAS) | `BootstrapServers=ns.servicebus.windows.net:9093;Type=EventHubSas;SharedAccessKeyName=...;SharedAccessKey=...;` |

Строка целиком — секрет, поэтому параметром её не передать: утилита берёт её из переменной окружения, в параметре — только имя переменной.

```bash
export REPLAY_SOURCE='BootstrapServers=...;Type=EventHubSas;SharedAccessKeyName=...;SharedAccessKey=...;'
export REPLAY_TARGET='BootstrapServers=...;'
dotnet run -- --source-env REPLAY_SOURCE --topic <топик> --from "…" --to "…" --routes routes.json --target-env REPLAY_TARGET
dotnet run -- --execute --plan run-…/plan.json --target-env REPLAY_TARGET
```

Настройки как у Dodo.Kafka: keepalive и обновление метаданных раз в 3 минуты (Azure закрывает простаивающие соединения), `client.id = kafka-replay`. В ошибках про строку подключения — только имена полей, значения не печатаются. `Type=EventHubAd` (вход через Azure AD) не поддерживается — понятный отказ.

## Контракты событий (`--contracts`)

Утилита проверяет события **заданной версией контрактов** — собранным реестром event-registry. Версия — это то, с какого коммита реестр собран:

```bash
cd <event-registry>
git checkout <версия, которую проверяем>
dotnet build src/Dodo.EventRegistry -c Release -o ~/replay-contracts -p:CopyLocalLockFileAssemblies=true

dotnet run -- --bootstrap … --topic <топик> --from "…" --to "…" --contracts ~/replay-contracts/Dodo.EventRegistry.dll
```

- Контракты загружаются в отдельный `AssemblyLoadContext`; типы полей всех событий проверяются сразу, поэтому ошибка «не хватает сборки» будет до чтения топика.
- В отчёте у каждого события: версия пакета из `Event-PackageVersion` и версия контракта, которым его прочитали; пометка, если по реестру тип живёт в другом топике.

Проверить загрузку на настоящих классах без кластера: `cd Seeder && dotnet run -- --contracts ~/replay-contracts/Dodo.EventRegistry.dll` — по одному событию каждого типа в `registry-events`, затем команда для `replay` из вывода Seeder.

## Таблица маршрутизации

`routes.json` — тип события (как в `Event-Type`) → целевой топик; `*` — для всех остальных наших событий:

```json
{
  "MessageCheck.SampleContracts.OrderCreated": "orders-copy",
  "MessageCheck.SampleContracts.OrderCancelled": "orders-copy"
}
```

В план попадают только разрешённые проверкой записи, для которых есть маршрут. Целевые топики должны существовать (утилита их не создаёт; число партиций нужно, чтобы выбрать партицию заранее). Маршрут в топик-источник того же кластера — блок ещё до чтения.

## Отправка, статусы, повторный запуск

`--execute` читает **только** `plan.json`: источник заново не читается и не проверяется.

1. Пересчитываются суммы каждой строки и всего плана. **Любое несовпадение — ничего не отправляется**, код 3.
2. Цель должна совпадать с целью плана.
3. Отправка с `Acks.All` и идемпотентным продюсером, в исходном порядке, с исходным временем, ключом и заголовками.
4. Статусы — в `execution.json` рядом с планом:

| Статус | Когда | При повторном запуске |
|---|---|---|
| записано | брокер подтвердил (`Persisted`) | не отправляется |
| точно не записано | брокер отказал (`NotPersisted`) | отправляется снова |
| результат неизвестен | подтверждения нет (`PossiblyPersisted`, таймаут, падение посреди отправки) | **не отправляется автоматически** — проверить цель вручную |
| отклонено проверкой | Rejected или ConversionError | — |
| не отправлялось | чужое событие, tombstone, нет маршрута | — |

Перед отправкой вся пачка помечается «результат неизвестен» и сохраняется: если утилита упадёт посреди отправки, при перезапуске эти строки не уйдут второй раз.

5. **Побайтовая сверка:** по адресу из подтверждения (партиция, offset) запись читается из цели и сравнивается с планом — ключ, заголовки (имена, значения, порядок), тело. Расхождение времени показывается, но на совпадение не влияет.

## Отчёты

- `report.md` — читабельный для людей: сводки, таблица записей, подробно по каждой записи (исходник, JSON после чтения, отличия или почему их нет, решение, статус). Шаблон и три сценария — [`docs/report-template.md`](docs/report-template.md).
- `report.json` — то же самое, плюс план чтения по партициям (low, high, start, end) и контрольные суммы: `payloadSha256` (тело), `recordSha256` (ключ, заголовки, тело).
- `plan.json` — план отправки: исходные байты (base64), решения, цели, суммы строк и всего плана.
- `execution.json`, `execution.md` — статусы и результаты сверки.

Сводки сходятся, если число записей по решениям, по статусам и по строкам таблицы «тип × версия × цель × статус» равно числу прочитанных записей.

## Проверка на дампе Event Hubs Capture

Скрипты в `scripts/` перекладывают выгрузку Event Hubs Capture (Avro) в локальную Kafka и сравнивают прогоны. Скрипты не печатают содержимое сообщений — только количества, имена полей и типов.

```bash
python3 -m venv ~/avro-env && . ~/avro-env/bin/activate && pip install fastavro confluent-kafka

python3 -I scripts/avro_survey.py <папка топика в дампе>                         # записи, заголовки, типы, время, ключи
python3 -I scripts/avro_load.py <папка топика> --topic <топик>                   # 1 партиция, как в дампе
python3 -I scripts/avro_load.py <папка топика> --topic <топик>-p4 --partitions 4  # N партиций, партиция по ключу (CRC32, как .NET)
python3 -I scripts/compare_runs.py --one <run-1>/report.json --many <run-4>/report.json [--plan <plan.json>]
python3 -I scripts/keys_spread.py <папка топика>                                  # как ключи расходятся по N партициям при CRC32 и murmur2
```

- `avro_load.py`: тело и заголовки — как есть, ключ — из `x-opt-kafka-key`, время сообщения — исходное время записи в Event Hubs; топик создаётся с `retention.ms=-1`. Каждый топик дампа грузится в свой топик.
- `compare_runs.py` проверяет, что на 1 и на N партициях одни и те же сообщения, вердикты и отличия, что каждый ключ лежит в одной партиции (`CRC32(ключ) % N`), что порядок внутри ключа сохранён и (с `--plan`) что утилита выбирает партицию так же, как Kafka-клиент.
- Запускайте `replay` на небольших окнах (минуты–сутки): сейчас отчёт пишет подробности по каждой записи.

## Вопросы и предложения

1. **Окно по времени и непорядок во времени.** Окно переводится в offsets: `[первый с временем ≥ from; первый с временем ≥ to)`, границы фиксируются до чтения. Сообщение *внутри* этого диапазона со временем вне окна помечается `⚠ время вне окна`. Но если время в партиции идёт не по порядку (CreateTime от продюсера, репликация), сообщение со временем *внутри* окна может лежать *после* правой границы — утилита его не прочитает и не предупредит. В Event Hubs время в партиции монотонное; в Kafka с CreateTime — не гарантировано. План: дочитывать за правой границей с запасом и предупреждать / не давать код 0.
2. **Пустое окно** даёт `✅` и код 0 — стоит предупреждать.
3. **Размер отчёта.** Подробности по каждой записи: на сотнях тысяч сообщений `report.md` — сотни мегабайт. Нужен режим «только сводка» (счётчики по типам и полям + примеры).
4. **Часовой пояс машины.** Если в контракте поле `DateTime`, а в событии время со смещением, System.Text.Json переводит его в пояс машины — отличие видно или нет в зависимости от того, где запущена утилита.
5. **Вычисляемые поля** контракта (поле отсутствует в событии, но класс заполняет его из другого поля) помечаются как «значение по умолчанию ⚠» — возможна ложная тревога.

## Уверенно принятое

- JSON читается как в Dodo.Kafka: System.Text.Json с настройками по умолчанию, регистр имён важен, лишние поля пропускаются (но видны в отчёте).
- Класс события выбирается по `Event-Type`; `Event-PackageVersion` — только для отчёта.
- Заголовки переносятся как есть, новые не добавляются — иначе не будет совпадения байт в байт. Время записи переносится исходное.
- Tombstone не переносятся (статус «не отправлялось»).
- Запрет «в источник» — по совпадению топика **и** кластера (адреса BootstrapServers).

## Структура

```
KafkaReplay.slnx            — все проекты репозитория
Directory.Build.props       — общие настройки: net10, nullable, анализаторы, предупреждения = ошибки
Directory.Packages.props    — версии всех пакетов
.editorconfig               — стиль кода
KafkaReplay/
  src/KafkaReplay/          — утилита (программа replay)
  tests/KafkaReplay.Tests/  — тесты утилиты
  tests/SampleRegistry/     — учебный реестр контрактов для тестов (устроен как Dodo.EventRegistry)
  samples/routes.json       — таблица маршрутизации для демо
MessageCheck/               — проверка одной записи: заголовки → каталог → контракт → решение, отличия; загрузка контрактов
Seeder/                     — тестовые события: учебные или по реестру контрактов
scripts/                    — demo.sh (весь цикл), скрипты для дампа Event Hubs Capture
docs/report-template.md     — шаблон отчёта (три сценария)
learning/                   — первые две недели: Producer/Consumer/CrashTest, RangeReader (Assign без коммита, offset группы до/после), сравнение kcat / Kafbat UI / Redpanda Connect (tools.md)
docker-compose.yml          — локальная Kafka и интерфейсы
```
