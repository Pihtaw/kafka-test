# KafkaReplay

`replay` — утилита для переноса событий между топиками Kafka с проверкой контрактами. Читает события за интервал времени, проверяет их заданной версией контрактов, строит план отправки, отправляет по нему и побайтово сверяет результат.

Работа идёт в два шага:

1. `replay check` — чтение, проверка, отчёт и план отправки. Ничего не отправляет.
2. `replay execute` — отправка строго по плану и побайтовая сверка. Источник повторно не читается.

## Требования

- .NET 10 SDK
- Docker — для локальной Kafka и демо

## Установка

Утилита собирается как dotnet tool:

```bash
dotnet pack KafkaReplay/src/KafkaReplay -c Release -o nupkg
dotnet tool install --global KafkaReplay --add-source ./nupkg
replay --help
```

Обновление — `dotnet tool update --global KafkaReplay --add-source ./nupkg`, удаление — `dotnet tool uninstall --global KafkaReplay`.

Без установки: `dotnet run --project KafkaReplay/src/KafkaReplay -- <команда> …`.

## Демо

```bash
dotnet test
scripts/demo.sh
```

`demo.sh` поднимает Kafka в Docker, записывает 15 учебных событий и выполняет полный цикл: `check` (код 1 — в данных есть заведомо битые события), `execute` (код 0), повторный `execute` (ничего не отправляет, код 0). Порт 9092 должен быть свободен.

## Запуск

**Подготовка.**
- Контракты: `scripts/build-contracts.sh <путь к event-registry>` — сборка нужной версии реестра появится в `contracts/` (папка не попадает в git).
- Подключение: для Kafka без авторизации — `--bootstrap host:port`. Для Event Hubs строка подключения передаётся через переменную окружения, в параметре указывается только её имя: `--source-env REPLAY_SOURCE`, где `REPLAY_SOURCE='BootstrapServers=...;Type=EventHubSas;SharedAccessKeyName=...;SharedAccessKey=...;'`.
- Целевой топик создаётся заранее: утилита топики не создаёт.

**1. Проверка:**

```bash
replay check --bootstrap <kafka> --topic <источник> \
  --from "2026-10-28 14:21:45+00:00" --to "2026-10-28 14:21:46+00:00" \
  --contracts contracts/Dodo.EventRegistry.dll --out run-check
```

Результат — `report.md` и `report.json`: решение по каждому событию и отличия, которые увидит сервис.

**2. План отправки** — та же команда с таблицей маршрутов и целью:

```bash
replay check … --routes routes.json --target-bootstrap <kafka> --out run-plan
```

`routes.json` сопоставляет тип события (как в `Event-Type`, с учётом регистра) и целевой топик; `null` — не отправлять, `*` — все остальные типы:

```json
{ "<Тип события>": "<целевой топик>", "<Ненужный тип>": null }
```

План не строится, если для типа из данных нет записи в таблице, если в папке `--out` уже есть план от прошлого запуска или если нет целевого топика (код 3, причина в выводе).

**3. Отправка:**

```bash
replay execute --plan run-plan/plan.json --target-bootstrap <kafka>
```

Повторный запуск с тем же планом отправляет только то, что не было записано, поэтому его можно повторять.

Пример на тестовом стенде: 2935 событий, все прошли проверку, отправлены в топик из 3 партиций, совпали байт в байт; повторный `execute` ничего не отправил.

## Параметры

Полный список — `replay <команда> --help`.

| `check` | |
|---|---|
| `--topic`, `--from`, `--to` | источник и окно `[from; to)`; время с часовым поясом (обязательно) |
| `--bootstrap` / `--source-env` | подключение к источнику |
| `--contracts` | сборка контрактов; без неё используются учебные контракты |
| `--routes`, `--target-bootstrap` / `--target-env` | таблица маршрутов и цель — для построения плана |
| `--partitioner` | выбор партиции в цели: `crc32` (по умолчанию), `murmur2`, `keep` |
| `--tail` | сколько записей после окна просмотреть в поиске опоздавших событий (по умолчанию 10000, `all` — до конца) |
| `--schemas` | папка с JSON-схемами (см. ниже) |
| `--out` | папка для результатов |

| `execute` | |
|---|---|
| `--plan` | путь к `plan.json` (обязательно) |
| `--target-bootstrap` / `--target-env` | цель; должна совпадать с целью плана |

| `schemas` | |
|---|---|
| `--contracts` | сборка контрактов (обязательно) |
| `--out` | папка для схем, по умолчанию `contracts/schemas` |

## Коды выхода

| Код | `check` | `execute` |
|---|---|---|
| 0 | всё прочитано, отказов нет | всё записано и совпало |
| 1 | есть отклонённые события | есть незаписанные, неизвестные или несовпавшие записи |
| 2 | окно прочитано не полностью | статусы не сходятся |
| 3 | ошибка параметров или план строить нельзя | ошибка параметров или план нельзя отправлять |

## Статусы отправки

| Статус | Значение | При повторном `execute` |
|---|---|---|
| записано | брокер подтвердил запись | не отправляется |
| точно не записано | брокер отказал | отправляется |
| результат неизвестен | подтверждения нет | не отправляется автоматически; требует ручной проверки цели |
| отклонено проверкой | событие не прошло проверку | — |
| не отправлялось | не наше событие, tombstone, `null` в маршрутах, остановка после ошибки | строки плана отправляются |

Отправка идёт пачками; при ошибке в пачке отправка останавливается, чтобы сохранить порядок в партиции.

## JSON-схемы

Проверка по схеме дополняет проверку контрактом: она находит, например, `null` в полях, которые в контракте не допускают `null`.

```bash
replay schemas --contracts contracts/Dodo.EventRegistry.dll
replay check … --contracts contracts/Dodo.EventRegistry.dll --schemas contracts/schemas
```

Схемы генерируются из классов контрактов. Нарушения попадают в отчёт как предупреждения и не блокируют отправку. Вместо сгенерированных можно использовать официальные схемы — положить их в ту же папку.

## Принятые решения

- Тип события определяется по `Event-Type` с учётом регистра, как в Dodo.Kafka.
- Поддерживается тело JSON в UTF-8 (`Content-Type`, `Content-Encoding`); другие форматы отклоняются с понятной причиной.
- Ключ, заголовки и тело переносятся без изменений. Время записи в цели — время отправки; исходное время события сохраняется в заголовке `Event-Timestamp` и в теле.
- Tombstone не переносятся.
- Отправка в топик-источник запрещена; топики не создаются автоматически.

## Известные ограничения

- Пустое окно не даёт предупреждения.
- Отчёт содержит подробности по каждому событию и на больших окнах получается объёмным.
- «Результат неизвестен» разбирается вручную.
